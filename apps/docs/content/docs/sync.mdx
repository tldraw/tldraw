You can add realtime multi-user collaboration to your tldraw app by using **tldraw sync**. It's our library for fast, fault-tolerant shared document syncing. We use it in production on our flagship app [tldraw.com](https://tldraw.com).

We offer a [hosted demo](/docs/collaboration) of tldraw sync which is suitable for prototyping. To use tldraw sync in production, you will need to host it yourself.

## Deploying tldraw sync

There are two main ways to go about hosting tldraw sync:

1. Deploy a full backend to Cloudflare using our template (recommended).
2. Integrate tldraw sync into your own JavaScript backend using our examples and docs as a guide.

### Use our Cloudflare template

The best way to get started hosting your own backend is to clone and deploy [our Cloudflare template](https://github.com/tldraw/tldraw/tree/main/templates/sync-cloudflare). The template provides the same setup that runs on tldraw.com.

It uses:

- [Durable Objects](https://developers.cloudflare.com/durable-objects/) to provide a unique WebSocket server per room. Room state is persisted automatically to the durable object's built-in SQLite storage.
- [R2](https://developers.cloudflare.com/r2/) to store large binary assets like images and videos.

There are some features that we have not provided and you might want to add yourself, such as authentication and authorization, rate limiting and size limiting for asset uploads, storing snapshots of documents over time for long-term history, and listing and searching for rooms.

Make sure you also read the section below about [deployment concerns](#deployment-concerns).

[Get started with the Cloudflare template](https://github.com/tldraw/tldraw/tree/main/templates/sync-cloudflare).

### Integrate tldraw sync into your own backend

We recommend Cloudflare. The `@tldraw/sync-core` library also integrates tldraw sync into any JavaScript server environment that supports WebSockets.

We have a [simple Node.js server example](https://github.com/tldraw/tldraw/tree/main/templates/simple-server-example) to use as a reference for how things should be stitched together.

## What does a tldraw sync backend do?

A backend for tldraw sync consists of two or three parts:

- A **WebSocket server** that provides rooms for each shared document, and is responsible for synchronizing and persisting document state.
- An **asset storage** provider for large binary files like images and videos.
- (If using the built-in bookmark shape) An **unfurling service** to extract metadata about bookmark URLs.

On the frontend, there is just one part: the **sync client**, created using the [useSync](?) hook from the `@tldraw/sync` package.

Here's a simple client implementation:

```tsx
import { Tldraw, TLAssetStore, Editor } from 'tldraw'
import { useSync } from '@tldraw/sync'
import 'tldraw/tldraw.css'
import { uploadFileAndReturnUrl } from './assets'
import { convertUrlToBookmarkAsset } from './unfurl'

function MyEditorComponent({ myRoomId }: { myRoomId: string }) {
	// This hook creates a sync client that manages the websocket connection to the server
	// and coordinates updates to the document state.
	const store = useSync({
		// This is how you tell the sync client which server and room to connect to.
		uri: `wss://my-custom-backend.com/connect/${myRoomId}`,
		// This is how you tell the sync client how to store and retrieve blobs.
		assets: myAssetStore,
	})
	// When the tldraw Editor mounts, you can register an asset handler for the bookmark URLs.
	return <Tldraw store={store} onMount={registerUrlHandler} />
}

const myAssetStore: TLAssetStore = {
	upload(asset, file) {
		return uploadFileAndReturnUrl(file)
	},
	resolve(asset) {
		return asset.props.src
	},
}

function registerUrlHandler(editor: Editor) {
	editor.registerExternalAssetHandler('url', async ({ url }) => {
		return await convertUrlToBookmarkAsset(url)
	})
}
```

And [here's a full working example](https://github.com/tldraw/tldraw/blob/main/templates/simple-server-example/src/client/App.tsx) of the client-side code.

### WebSocket server

The `@tldraw/sync-core` package exports a class called [TLSocketRoom](?) that should be created server-side on a per-document basis.

`TLSocketRoom` stores the authoritative copy of the document, relays changes between sync clients over WebSockets, and exposes hooks for persisting the document when it changes.

Attach each incoming WebSocket to the room and forward its events:

```tsx
room.handleSocketConnect({ sessionId, socket })
// If your platform doesn't let the room add listeners to the socket itself
// (Bun.serve, Cloudflare hibernation), forward events by hand:
room.handleSocketMessage(sessionId, message, socket)
room.handleSocketClose(sessionId, socket)
```

<Callout type="info">
	You should make sure that there's only ever one `TLSocketRoom` globally for each room in your app.
	If there's more than one, users won't see each other and will overwrite others' changes. We use
	[Durable Objects](https://developers.cloudflare.com/durable-objects/) to achieve this on
	tldraw.com.
</Callout>

Read the reference docs for [TLSocketRoom](?), and see an example of how to use it in the [simple server example](https://github.com/tldraw/tldraw/blob/main/templates/simple-server-example/src/server/rooms.ts).

### Storage backends

`TLSocketRoom` requires a storage backend to persist document state. The `@tldraw/sync-core` package provides two options:

#### InMemorySyncStorage (default)

[InMemorySyncStorage](?) keeps all document state in memory. It's simple to use, but data is lost when the process restarts. To persist data, pass an `onChange` callback to the constructor and save snapshots to your database.

```tsx
import { InMemorySyncStorage, TLSocketRoom } from '@tldraw/sync-core'

const storage = new InMemorySyncStorage({
	snapshot: existingData, // optional: load from your database
	onChange() {
		// Save to your database when changes occur
		saveToDatabase(storage.getSnapshot())
	},
})

const room = new TLSocketRoom({ storage })
```

#### SQLiteSyncStorage (recommended for persistence)

[SQLiteSyncStorage](?) stores document state in SQLite. Data survives process restarts automatically. This is the recommended approach for production deployments.

##### Cloudflare Durable Objects

```tsx
import { DurableObject } from 'cloudflare:workers'
import { SQLiteSyncStorage, DurableObjectSqliteSyncWrapper, TLSocketRoom } from '@tldraw/sync-core'

export class TLSyncDurableObject extends DurableObject {
	private room: TLSocketRoom

	constructor(ctx: DurableObjectState, env: Env) {
		super(ctx, env)
		const sql = new DurableObjectSqliteSyncWrapper(ctx.storage)
		const storage = new SQLiteSyncStorage({ sql })
		this.room = new TLSocketRoom({ storage })
	}
}
```

##### Node.js with better-sqlite3 or node:sqlite

```tsx
import Database from 'better-sqlite3' // replace with 'node:sqlite' if using
import { SQLiteSyncStorage, NodeSqliteWrapper, TLSocketRoom } from '@tldraw/sync-core'

const db = new Database('rooms.db')
const sql = new NodeSqliteWrapper(db)
const storage = new SQLiteSyncStorage({ sql })
const room = new TLSocketRoom({ storage })
```

<Callout type="info">
	`SQLiteSyncStorage` automatically creates and manages its database tables. You can pass a
	`tablePrefix` option to the SQL wrapper to avoid conflicts if you're sharing a database with other
	data.
</Callout>

### WebSocket hibernation

Some serverless platforms let WebSocket connections survive while the surrounding object hibernates. [Cloudflare Durable Objects](https://developers.cloudflare.com/durable-objects/best-practices/websockets/) is the most common example. The platform keeps the sockets open, but your in-memory state (including the `TLSocketRoom`) is gone when the object wakes back up. Without help, every wake forces every client to reconnect.

`TLSocketRoom` exposes three APIs for hibernation. The `onSessionSnapshot` callback fires when a session has had no message activity for about 5 seconds, so you can persist its state. [TLSocketRoom#getSessionSnapshot](?) returns that snapshot on demand. [TLSocketRoom#handleSocketResume](?) restores a session straight into `Connected` state when the object wakes back up.

Here's the pattern in a Cloudflare Durable Object that uses the WebSocket Hibernation API:

```tsx
import {
	DurableObjectSqliteSyncWrapper,
	type SessionStateSnapshot,
	SQLiteSyncStorage,
	TLSocketRoom,
} from '@tldraw/sync-core'
import { TLRecord } from '@tldraw/tlschema'
import { DurableObject } from 'cloudflare:workers'

interface SocketAttachment {
	sessionId: string
	snapshot?: SessionStateSnapshot
}

export class TldrawDurableObject extends DurableObject {
	private room: TLSocketRoom<TLRecord, void> | null = null
	// Maps sessionId → ws. Set it on connect and on resume, never from webSocketMessage: a
	// superseded socket for the same session id can still deliver messages.
	private readonly sessionIdToWs = new Map<string, WebSocket>()

	private getOrCreateRoom() {
		if (this.room) return this.room

		const sql = new DurableObjectSqliteSyncWrapper(this.ctx.storage)
		const storage = new SQLiteSyncStorage<TLRecord>({ sql })

		this.room = new TLSocketRoom<TLRecord, void>({
			storage,
			// Cloudflare keeps WebSockets alive across hibernation, so let it manage timeouts.
			clientTimeout: Infinity,
			// Persist each session's snapshot to its WebSocket attachment when it goes idle.
			onSessionSnapshot: (sessionId, snapshot) => {
				const ws = this.sessionIdToWs.get(sessionId)
				if (ws) ws.serializeAttachment({ sessionId, snapshot })
			},
		})

		// Resume any sessions whose sockets survived hibernation.
		for (const ws of this.ctx.getWebSockets()) {
			const attachment = ws.deserializeAttachment() as SocketAttachment | null
			if (attachment?.snapshot) {
				this.room.handleSocketResume({
					sessionId: attachment.sessionId,
					socket: ws,
					snapshot: attachment.snapshot,
				})
				this.sessionIdToWs.set(attachment.sessionId, ws)
			}
		}

		return this.room
	}
}
```

Three pieces make this work. The `onSessionSnapshot` callback persists each session's state to its WebSocket's attachment so the snapshot is still around after hibernation. When the object wakes up with sockets still open, `handleSocketResume` replays each saved snapshot and the session lands straight in `Connected` state; the client never sees a reconnect. Setting `clientTimeout: Infinity` disables the room's idle timer; hibernating platforms handle keep-alive themselves and would otherwise see the room disconnect healthy clients.

For a complete implementation, including the connect handler and the hibernation event handlers that pass each socket to the room, see the [sync-cloudflare template](https://github.com/tldraw/tldraw/tree/main/templates/sync-cloudflare).

For non-hibernating environments (Node servers, long-lived processes), you don't need any of this. The in-memory `TLSocketRoom` outlives individual sockets, and the default `clientTimeout` (20 seconds) removes idle sessions.

## Using tldraw sync in your app

### Custom shapes & bindings

`@tldraw/sync` validates the contents of your document and runs migrations to make sure clients of
different versions can collaborate without issue. To support this, you need to make sure that both
the sync client and server know about any custom shapes or bindings you've added.

#### On the client

You can pass `shapeUtils` and `bindingUtils` props to `useSync`. Unlike `<Tldraw />`,
these don't automatically include tldraw's default shapes like arrows and rectangles. You should
pass those in explicitly if you're using them:

```tsx
import { useMemo } from 'react'
import { Tldraw, defaultShapeUtils, defaultBindingUtils } from 'tldraw'
import { useSync } from '@tldraw/sync'

function MyApp() {
	const store = useSync({
		uri: '...',
		assets: myAssetStore,
		shapeUtils: useMemo(() => [...customShapeUtils, ...defaultShapeUtils], []),
		bindingUtils: useMemo(() => [...customBindingUtils, ...defaultBindingUtils], []),
	})

	return <Tldraw store={store} shapeUtils={customShapeUtils} bindingUtils={customBindingUtils} />
}
```

#### On the server

Use [createTLSchema](?) to create a store schema, and pass that into [TLSocketRoom](?). You can
use shape/binding utils here, but the schema only reads three properties:
[`props`](/reference/editor/ShapeUtil#props), `meta`, and
[`migrations`](/sdk-features/persistence#Migrations). You need to provide the default shape
schemas if you're using them.

```tsx
import { createTLSchema, defaultShapeSchemas, defaultBindingSchemas } from '@tldraw/tlschema'
import { TLSocketRoom } from '@tldraw/sync-core'

const schema = createTLSchema({
	shapes: {
		...defaultShapeSchemas,

		myCustomShape: {
			// Validations for this shape's `props`.
			props: myCustomShapeProps,
			// Migrations between versions of this shape.
			migrations: myCustomShapeMigrations,
		},

		// The schema knows about this shape, but it has no migrations or validation.
		mySimpleShape: {},
	},
	bindings: defaultBindingSchemas,
})

// Later, in your app server:
const room = new TLSocketRoom({
	schema: schema,
	// ...
})
```

Both `props` and `migrations` are optional. If you omit `props`, you won't have any server-side
validation for your shape, which could result in bad data being stored. If you omit `migrations`,
clients on different versions won't be able to collaborate without errors.

### Who may change what

Every change a client pushes is a batch of record operations: create, update, or delete one record each. The room decides, for each operation, whether to store it. You control that in two ways: access set at connect, and a rule you write.

#### Access set at connect

A room keeps records in two places: the document (every document-scoped type in your schema) and, if you list `objectTypes`, the object store (see [Comments and the object-store lane](#comments-and-the-object-store-lane)). The simplest control is write access to each, per session, decided by your server at connect:

```ts
// on your server, when the WebSocket upgrade request arrives
const { userId, userCanEdit } = await authenticate(request)

room.handleSocketConnect({
	sessionId,
	socket,
	userId,
	access: { document: userCanEdit ? 'write' : 'read', objects: userId ? 'write' : 'read' },
})
```

`userId` is the authenticated user, from your own auth, or `null` for anonymous (the default). The room doesn't check it; it hands it to your rule as `session.userId` and keeps it across hibernation.

A session with `document: 'read'` can't change the document, and one with `objects: 'read'` can't change the object store. The room refuses a push that writes to either, whole, whether or not you also give it a rule. The client receives the same object (as `access` on the `useSync` status) and locks its toolbar from it. The two are independent; rooms without object types give `objects` the same value as `document`.

`access` is fixed for the life of the connection. To change it, call [TLSocketRoom#closeSession](?) without a reason: the client reconnects and you pass new values. `isReadonly` and `objectAccess` are the same two facts under their previous names, deprecated but working until a later major.

#### Writing your own rule

For anything finer than that, give the room one rule with the `authorize` option. The room calls it once per push, inside the commit transaction, with every change in the push. Return `null` to allow the push, or `{ reason, ids? }` to refuse all of it: nothing is stored, and the client is told why.

Most rules are about one record at a time. `perRecord` builds a push rule from one of those: return `null` to allow the change or a reason to refuse it.

What a session may do usually comes from your server as a list of named permissions, passed at connect. tldraw's own are `tl:shape:create`, `tl:shape:update`, `tl:shape:delete` and the same three for `tl:page`; a name ending in `:*` covers everything under it, and you can add names of your own under another prefix. `isChangePermitted` from `@tldraw/permissions` checks a change against the list, and `getRequiredPermission` names the permission it needs, for the refusal:

```ts
import { getRequiredPermission, isChangePermitted } from '@tldraw/permissions'
import { perRecord, TLSocketRoom } from '@tldraw/sync-core'

// students draw, but pages are the teacher's
const authorize = perRecord<TLRecord>((change, { session }) => {
	return isChangePermitted(session.permissions, change)
		? null
		: `Needs ${getRequiredPermission(change)}`
})

const room = new TLSocketRoom<TLRecord>({ objectTypes, authorize })

room.handleSocketConnect({
	sessionId,
	socket,
	userId: user.id,
	access,
	permissions: user.role === 'teacher' ? ['tl:*'] : ['tl:shape:*'],
})
```

The permissions are sent to the client too, so the same rule gives the same answer in the editor, and the UI can follow them (see [Showing what someone can do](#showing-what-someone-can-do)). For facts you don't want the client to see, pass `meta` instead: the rule reads it as `session.meta`, and it never leaves the server.

Leave `permissions` out and they're `null`: the app doesn't use named permissions, and nothing about them changes for that session. `[]` is different: granted nothing. `isPermitted` and `isChangePermitted` treat `null` as nothing granted too, so if one of your connect paths forgets the list, a rule that asks refuses rather than letting everything through. Watch out for `user.permissions ?? []` in your server code: it turns "not in use" into "nothing allowed".

The rule only sees pushes the session's access allows, so it can only narrow what `access` grants, never widen it. Combine several rules with `composeRules` from `@tldraw/permissions`: the first refusal wins.

What the rule sees:

| Argument              | What it is                                                                                                                                                           |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `changes`             | every change in the operation, one per record, as `{ type, prev, next }`; `type` is `'create'`, `'update'` or `'delete'`, `prev` is null on create, `next` on delete |
| `session.userId`      | the authenticated user from connect, or `null` for anonymous                                                                                                         |
| `session.permissions` | the named permissions from connect, or from the latest `updateSessionPermissions`; also sent to the client. `null` when not in use                                   |
| `session.meta`        | whatever else your server attached at connect; the room never reads it, and it isn't sent to the client                                                              |
| `session.access`      | the document and object store access from connect                                                                                                                    |
| `before(id)`          | any record as it was before the operation                                                                                                                            |
| `after(id)`           | any record as it will be once the operation is applied                                                                                                               |

A `perRecord` rule gets one change (plus `record`: `next`, or `prev` on a delete) and the same `session`, `before` and `after`.

The room judges a push one operation at a time. An operation is one editor action (one `editor.run`, side effects included), and a push holds every operation the client made since its last push, in order. The rule sees each operation with the earlier ones already applied. Consecutive operations that only update the same records, like the steps of a drag, arrive as one. An older client sends its whole push as a single operation.

The session id is chosen by the client and carries no authority; identity is `session.userId`. The rule runs on every operation in every push: keep it fast and synchronous, and do no I/O. If it throws, the operation is refused and the error is logged.

#### Fields the client must not choose

For a field the client must not choose, like an owner, check it in the rule: the client writes its own user id, and the rule refuses a create with anyone else's and any later change to it. The client becomes no more trusted; the room only accepts the right value, and the editor doesn't have to wait for the server to know it.

```ts
const authorize = perRecord<TLRecord>(({ type, prev, next }, { session }) => {
	if (next?.typeName !== 'shape') return null
	if (type === 'create' && next.meta.createdBy !== session.userId) return 'not your id'
	if (type === 'update' && next.meta.createdBy !== prev.meta.createdBy) return 'createdBy is fixed'
	return null
})
```

The room never rewrites what a client sends, so a value only the server can know, like when it received a record, isn't part of a push. Your server can write it afterwards with [TLSocketRoom#updateStore](?).

#### Rules that read other records

`before` and `after` are what let you write rules about pages: a shape's record names its parent, which may be a frame, whose parent may be a group, whose parent is the page. [getOwningPage](?) from `@tldraw/permissions` does that walk. Read `prev` through `before` and `next` through `after`, so a change is judged against the board it leaves and the board it lands on.

```ts
import { getOwningPage, isPermitted } from '@tldraw/permissions'

const authorize = perRecord<TLRecord>(({ prev, next }, { session, before, after }) => {
	// a permission of your own, granted to teachers at connect
	if (isPermitted(session.permissions, 'classroom:manage')) return null
	// the page's policy is stored on the page record, so only a teacher may change it
	if (next?.typeName === 'page' && next.meta.ownerId !== prev?.meta.ownerId) return 'teachers only'
	// check both ends of the change, so a shape can't be moved off a page the student doesn't own
	for (const [end, get] of [
		[prev, before],
		[next, after],
	] as const) {
		if (!end) continue
		const owning = getOwningPage(get, end)
		// a broken parent chain: refuse, the write would leave an orphan
		if (!owning.page) return owning.reason === 'unscoped' ? null : 'dangling parent'
		// students may only change records on their own page
		if (owning.page.meta.ownerId !== session.userId) return 'not your page'
	}
	return null
})
```

Here the page's policy lives on the page record, in its `meta`. Any client can send a change to that record, so the rule is what makes the field trustworthy: refuse policy changes from anyone but a trusted role, as the second line does. That line is enough on its own. The room refuses an operation that forges the policy and every operation after it in the same push, so nothing built on the forged policy is stored.

Because the rule sees a whole operation, the order of changes inside it never matters. A frame and the shapes inside it can be created in either order; a frame deleted together with its children goes, children and all; a shape reparented into a frame the same operation deletes is refused.

`getOwningPage` returns `{ page }` or `{ page: null, reason }`. The reason is `'dangling'` when a parent is missing (refuse: the write would leave an orphan), `'split'` for a binding whose two shapes are on different pages (refuse: the editor never makes one), or `'unscoped'` for records that don't live on a page, like the document record (your call).

#### Keeping the document valid

Your rule decides who may change what. Whether a push leaves the document intact is a separate question with the same answer for every app: a shape needs a parent that exists, and a binding needs both its shapes on one page. `createStructureRule` from `@tldraw/permissions` refuses pushes that break those. Put it first:

```ts
import { composeRules, createStructureRule } from '@tldraw/permissions'

const room = new TLSocketRoom<TLRecord>({
	objectTypes,
	authorize: composeRules(createStructureRule(), authorize),
})
```

It only judges what a push changes, so a document that already has a broken record keeps working, and the edit that repairs it goes through. It doesn't yet check what a delete leaves behind (the children of a deleted frame, a binding to a deleted shape): that needs a lookup of what points at a record, which rooms don't have yet.

#### Permissions that change while people are connected

`access` is fixed for the connection, but permissions aren't. When a teacher hands a student a page, or a share link changes, update the session:

```ts
room.updateSessionPermissions(sessionId, ['tl:*'])
```

The rule judges that session's next push with the new list, and its client gets it right away, with no reconnect. Updates are per session, so they reach anonymous sessions too. To change a user's permissions in every tab they have open, update each of their sessions:

```ts
for (const session of room.getSessions()) {
	if (session.userId === userId) room.updateSessionPermissions(session.sessionId, permissions)
}
```

Each client only gets its own permissions. A session still connecting gets the latest list with its connect. With [hibernation](#websocket-hibernation), the list is part of the session snapshot: `onSessionSnapshot` gets a fresh one on every update, and if you save snapshots yourself, save one again after updating, or a resumed room brings back the old list.

#### What a refused push looks like

When the rule refuses an operation, the room stores the operations before it in the push and discards that one and every one after it. A later operation may build on the refused one, so the room doesn't judge the rest. The room tells the sending client in the `push_result`, with the rule's `reason` and `ids` and the index of the first refused operation. The client keeps what was stored and reverts the rest: the user sees those changes snap back. Pass `onPushRefused` to `useSync` (or `TLSyncClient`) to show a message. The server logs a warning. Only rooms using the deprecated `authorizeRecord` still skip refused records one at a time, silently.

#### What the rule never sees

- Server-side writes through [TLSocketRoom#updateStore](?) or [TLSocketRoom#loadSnapshot](?). These have no session and are never authorized; check permissions before calling them.
- Presence records (cursors, selections). They are per session and never authorized.
- Malformed records. Schema validation runs before the rule and disconnects the client with an error rather than refusing.

#### Running the rule in the editor

The same rule can run in the editor too, so a change the room would refuse is reverted before it's sent. Pass it to `useSync`:

```tsx
const store = useSync({ uri, assets, authorize: { rule: authorize } })
```

The room sends its `objectTypes` on connect, so the editor knows which records `access.objects` covers. The editor judges it the way the room does: the session's `access` first, then the rule. The unit is one editor operation (one `editor.run`, side effects included), so a group, a delete and its binding cleanup are judged whole. The session is what the server granted: `userId` and `access` from connect, and `permissions`, kept current as the server updates them. Until the first connect every change is refused. A rule that reads a database or other server-only data can only run on the server.

The room's `meta` isn't sent to the client, so `session.meta` is undefined in the editor. Keep `meta` for server-only facts; anything the editor's copy of the rule needs to know goes in `permissions`, as names of your own if needed (`classroom:manage`, `plan:pro`).

The write rule enforces submitted client changes on the server and configured local edits in the editor. The editor's check covers its own document writes, not uploads or other effects your code starts. The two also group changes differently, the editor by operation and the server by push, so their answers can differ. The room stays the authority: whatever the editor lets through, it judges again, and its answer is the one that counts.

When the editor refuses a change, it reverts it before history or sync see it, so there's nothing to undo and nothing is pushed. The interaction in progress ends, keeping what was accepted earlier in it: a drag stops where the last allowed frame put the shape. History is left as it was too, redo included, and an undo or redo the rule refuses changes nothing. Listen for both kinds of refusal with `editor.on('refused', ...)`; `source` is `'local'` or `'server'`.

Without sync, give the store its rule directly: `createTLStore({ authorize: { rule } })`, or the `authorize` prop on `<Tldraw />` when it creates the store. By default there is no user (`session.userId` is `null`) and access is `'write'`, and `permissions` is `null`, so a rule that reads `session.userId` or `session.permissions`, such as ownership, needs `getSession` too. So does an app that switches users or acts for an agent:

```tsx
<Tldraw
	authorize={{
		rule,
		getSession: () => ({ sessionId: 'local', userId, meta, access, permissions }),
	}}
/>
```

Changes made offline aren't judged again on reconnect. They're sent as one push, so if the room now refuses one of them (access or permissions changed in the meantime), it refuses all of them.

Client permissions need a tldraw license with the permissions feature, which collaboration licenses include. Without one the editor ignores `authorize`, `isChangePermitted` and `isPermitted`, and logs a warning; your server still enforces its rule. An [Editor](?) created outside `<TldrawEditor />` has no license manager, so it skips them too.

#### Showing what someone can do

The rule judges whole operations after the fact, so the UI can't ask it whether to show a button: one record on its own isn't the whole operation (deleting a frame also deletes its children). The editor asks two questions instead, before the user does anything:

- [Editor#isPermitted](?): is this kind of action available at all? For controls with no record yet: the new page button asks `tl:page:create`, the drawing tools ask `tl:shape:create` and `tl:shape:update`. A student holding `['tl:shape:*']` gets a disabled new page button.
- [Editor#isChangePermitted](?): may this record change this way? For controls tied to one shape or page: drag, resize, handles, text editing, the eraser, renaming or deleting a page. It gets the change as a rule sees one, `{ type: 'update', prev, next }`. With an ownership policy, your own shapes get handles and other people's don't.

Each is answered in this order:

1. Readonly and locked shapes, always.
2. Your app's `isPermitted` or `isChangePermitted` option, if you pass one.
3. Otherwise the session's permissions, [Editor#getPermissions](?), with the built-in mapping (`getRequiredPermission`), so the UI agrees with a rule that reads the same list and follows every update. There's nothing to pass:

   ```tsx
   <Tldraw store={store} />
   ```

4. With `null` permissions (not in use), everything is allowed.

A list of names covers `isPermitted` and the simple cases of `isChangePermitted`. Policies that depend on the record itself, like who owns it, which page it's on or a custom shape type, need your own `isChangePermitted`. `createPermissionPolicy` from `@tldraw/permissions` builds both options, for example with permissions for your own record types:

```tsx
const policy = createPermissionPolicy(undefined, { types: { sticker: 'stickers:edit' } })

<Tldraw store={store} isChangePermitted={policy.isChangePermitted} isPermitted={policy.isPermitted} />
```

Neither question stops anything: editor methods still try the change, and the rule decides. The UI can still offer something the rule then refuses, for example when permissions change or a record the operation depends on is protected. Selecting is never restricted.

The default UI follows both. Controls are disabled rather than hidden (readonly still hides them):

| Without           | What's off                                                                                                                                                                                                                                |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `tl:shape:create` | drawing tools, duplicate, paste, insert media and embed, group, frame selection, flatten, convert to bookmark or embed, double click for text, note clone handles; dropped and pasted files aren't handled at all, so nothing is uploaded |
| `tl:shape:update` | drawing tools (drawing updates the shape it creates on every frame), move, resize, rotate, restyle, reorder, align, flip, lock, group, ungroup, remove frame, move to page; replacing an image isn't handled                              |
| `tl:shape:delete` | delete, cut, the eraser, ungroup, remove frame, flatten, convert to bookmark or embed                                                                                                                                                     |
| `tl:page:create`  | new page, duplicate page, move to new page, alt+right past the last page                                                                                                                                                                  |
| `tl:page:update`  | rename, move and reorder pages                                                                                                                                                                                                            |
| `tl:page:delete`  | delete page                                                                                                                                                                                                                               |

Shapes `isChangePermitted` refuses get the same treatment one by one: no handles, no drag, no text editing, and the eraser skips them. A selection that mixes shapes the user can and can't change still drags, and the rule refuses the whole operation. The style panel is hidden when shapes can be neither created nor updated.

Your own tools can join in with `isEnabled` on the tool item: a disabled tool shows disabled in the toolbar and does nothing when selected, from a shortcut or anywhere else.

```tsx
tools.stamp = {
	...tools.stamp,
	isEnabled: (editor) =>
		editor.isPermitted('tl:shape:create') && editor.isPermitted('tl:shape:update'),
}
```

#### Keeping people off each other's shapes

A rule that allows creating shapes but not updating them can't draw: tools create a shape on pointer down and update it on every drag frame. To keep people off each other's shapes, write it as ownership instead. The editor stamps the creator on every shape the user creates, before the rule sees it, and the rule checks the stamp against the session:

```ts
// stamps meta.createdBy on shapes this user creates; copies become theirs
function stampOwnership(editor: Editor, getUserId: () => string | null) {
	// moveShapesToPage deletes and re-creates with the same ids: that's a move, keep the owner
	const recreated = new Map<TLShapeId, unknown>()
	editor.sideEffects.registerBeforeDeleteHandler('shape', (shape, source) => {
		if (source !== 'user') return
		if (recreated.size === 0) queueMicrotask(() => recreated.clear())
		recreated.set(shape.id, shape.meta.createdBy)
	})
	editor.sideEffects.registerBeforeCreateHandler('shape', (shape, source) => {
		// remote shapes keep the server's owner, undo restores the one it had
		if (source !== 'user' || editor.isReplayingHistory()) return shape
		const createdBy = recreated.has(shape.id) ? recreated.get(shape.id) : getUserId()
		return { ...shape, meta: { ...shape.meta, createdBy } }
	})
}

// yours to change, unless you manage the board; ownership itself never changes
const ownership: TLWriteRule<TLRecord> = ({ session, changes }) => {
	const me = session.userId
	const manage = isPermitted(session.permissions, 'board:manage')
	const mine = (shape: TLShape) => !!me && (shape.meta.createdBy === me || manage)
	for (const c of changes) {
		const shape = (c.next ?? c.prev) as TLShape
		if (shape.typeName !== 'shape') continue
		const ok =
			c.type === 'create'
				? !!me && (c.next.meta.createdBy === me || manage)
				: c.type === 'update'
					? mine(c.prev as TLShape) && c.next.meta.createdBy === c.prev.meta.createdBy
					: mine(c.prev as TLShape)
		if (!ok) return { reason: 'not yours', ids: [shape.id] }
	}
	return null
}
```

Run the stamp from `onMount` with the session's `userId`, not the attribution user. The rule is what makes the stamp trustworthy: the room refuses a create stamped with someone else's id. Anonymous sessions own nothing. Decide what undoing a deletion of someone else's shape should do: here it's allowed for whoever manages the board, since the restored shape keeps its owner.

### Comments and the object-store lane

A room can serve some record types through a second partition, the object-store lane, which is persisted and permissioned separately from the document. Comments are the main use for it.

Comment threads, comments, and reactions are record types that aren't in the default schema. Register
them with the `records` option on both ends: `useSync` on the client, [createTLSchema](?) on the
server. Both sides must register the same types, or the connection will fail schema validation.

```ts
import { TLSocketRoom } from '@tldraw/sync-core'
import { commentSchemaRecords, createTLSchema } from '@tldraw/tlschema'

const schema = createTLSchema({ records: commentSchemaRecords })

const room = new TLSocketRoom({
	schema,
	objectTypes: ['comment', 'comment-thread', 'comment-reaction'],
})
```

`objectTypes` serves those record types through the room's object-store lane instead of the document
lane. Lane records are persisted separately from the document, left out of document snapshots, and
gated by the session's `access.objects` rather than by `access.document`. That's how a session can
be allowed to comment without being allowed to edit:

```ts
room.handleSocketConnect({
	sessionId,
	socket,
	access: { document: 'read', objects: 'write' },
})
```

The lane's write access is `access.objects` at connect (`objectAccess` is its deprecated spelling), `'read'` or `'write'`, defaulting to `'write'`. Read the lane's contents with
[TLSocketRoom#getCurrentObjectsSnapshot](?), and use the room's `onCommittedChanges` callback to
mirror committed records into your own database. That callback only fires for client pushes, not for
`updateStore`, `loadSnapshot`, or direct storage writes. For per-record rules like "only the author
may edit a comment", write them in the room's `authorize` rule (see [Who may change what](#who-may-change-what)).
See [Commenting](/sdk-features/commenting) for the client side and the ready-made comment authorizers.

### Deployment concerns

<Callout type="warning">
	You must make sure that the tldraw version in your client matches the version on the server. We
	don't guarantee server backwards compatibility forever, and very occasionally we might release a
	version where the backend cannot meaningfully support older clients, in which case tldraw will
	display a "please refresh the page" message. So you should make sure that the backend is updated
	at the same time as the client, and that the new backend is up and running just before the new
	client rolls out.
</Callout>

### Migrating data from a legacy system

If you have been using some other solution for data sync, you can migrate your existing data to the tldraw sync format.

[SQLiteSyncStorage](?) accepts a [TLStoreSnapshot](?) directly, and [TLSocketRoom#loadSnapshot](?) accepts one for any storage backend, so you can add a backwards-compatibility layer that lazily imports data from your old system and converts it to a `TLStoreSnapshot`.

#### With SQLiteSyncStorage (recommended)

```tsx
import { SQLiteSyncStorage, NodeSqliteWrapper, TLSocketRoom } from '@tldraw/sync-core'
import Database from 'better-sqlite3'

function loadOrMakeRoom(roomId: string, db: Database.Database) {
	const sql = new NodeSqliteWrapper(db, { tablePrefix: `room_${roomId}_` })

	// Check if we already have data in SQLite
	if (SQLiteSyncStorage.hasBeenInitialized(sql)) {
		const storage = new SQLiteSyncStorage({ sql })
		return new TLSocketRoom({ storage })
	}

	// Try to load from legacy system
	const legacyData = loadRoomDataFromLegacyStore(roomId)
	if (legacyData) {
		const snapshot = convertOldDataToSnapshot(legacyData)
		const storage = new SQLiteSyncStorage({ sql, snapshot })
		deleteLegacyRoomData(roomId)
		return new TLSocketRoom({ storage })
	}

	// No data - create a new empty room
	return new TLSocketRoom({ storage: new SQLiteSyncStorage({ sql }) })
}
```

#### With InMemorySyncStorage

```tsx
import { InMemorySyncStorage, TLSocketRoom } from '@tldraw/sync-core'

async function loadOrMakeRoom(roomId: string) {
	// InMemorySyncStorage takes a RoomSnapshot, which is what getSnapshot() returns.
	const data = await loadRoomDataFromCurrentStore(roomId)
	if (data) {
		const storage = new InMemorySyncStorage({ snapshot: data })
		return new TLSocketRoom({ storage })
	}
	const legacyData = await loadRoomDataFromLegacyStore(roomId)
	if (legacyData) {
		// Convert your old data to a TLStoreSnapshot.
		const snapshot = convertOldDataToSnapshot(legacyData)
		// Load it into the room. loadSnapshot accepts a TLStoreSnapshot.
		const storage = new InMemorySyncStorage()
		const room = new TLSocketRoom({ storage })
		room.loadSnapshot(snapshot)
		// Save an updated copy of the snapshot in the new place
		// so that next time we can load it directly.
		await saveRoomData(roomId, storage.getSnapshot())
		// Optionally delete the old data.
		await deleteLegacyRoomData(roomId)
		// And finally return the room.
		return room
	}
	// If there's no data at all, just make a new blank room.
	return new TLSocketRoom({ storage: new InMemorySyncStorage() })
}
```

### Migrating from R2 to SQLite on Cloudflare

If you were previously using R2 to store room snapshots (as shown in earlier versions of the sync-cloudflare template), you can migrate to SQLite storage while preserving existing data.

#### Step 1: Update wrangler.toml if needed

If your Durable Object class was originally created _without_ SQLite support, you need to add a new migration with a new Durable Object class that uses SQLite storage.
You need to keep the old class for at least one release because it can't be deleted while it's still being used, but you can convert it to an empty class.

```toml
# Keep existing migration for old class
[[migrations]]
tag = "v1"
new_classes = ["TldrawDurableObject"]

# Add new migration for SQLite-backed class
[[migrations]]
tag = "v2"
new_sqlite_classes = ["TldrawDurableObjectSqlite"]

[durable_objects]
bindings = [
    # Point to the new SQLite-backed class
    { name = "TLDRAW_DURABLE_OBJECT", class_name = "TldrawDurableObjectSqlite" },
]
```

#### Step 2: Rename your Durable Object and add fallback loading

Rename your existing class (e.g. `TldrawDurableObject` → `TldrawDurableObjectSqlite`) and update the loading logic to check SQLite first, then fall back to R2:

```tsx
import {
	DurableObjectSqliteSyncWrapper,
	RoomSnapshot,
	SQLiteSyncStorage,
	TLSocketRoom,
} from '@tldraw/sync-core'
import { TLRecord, createTLSchema, defaultShapeSchemas } from '@tldraw/tlschema'
import { AutoRouter, error, IRequest } from 'itty-router'

// Empty stub for the old class name - required until migration is complete
export class TldrawDurableObject {}

const schema = createTLSchema({ shapes: defaultShapeSchemas })

// Renamed from TldrawDurableObject
export class TldrawDurableObjectSqlite {
	private roomPromise: Promise<TLSocketRoom<TLRecord, void>> | null = null
	private roomId: string | null = null

	constructor(
		private ctx: DurableObjectState,
		private env: Env
	) {
		// Load roomId from DO storage (needed for R2 fallback)
		ctx.blockConcurrencyWhile(async () => {
			this.roomId = (await ctx.storage.get('roomId')) as string | null
		})
	}

	// ... handleConnect, router, etc. stay the same ...

	private async loadRoom(): Promise<TLSocketRoom<TLRecord, void>> {
		const sql = new DurableObjectSqliteSyncWrapper(this.ctx.storage)

		// If SQLite already has data, use it directly
		if (SQLiteSyncStorage.hasBeenInitialized(sql)) {
			const storage = new SQLiteSyncStorage<TLRecord>({ sql })
			return new TLSocketRoom<TLRecord, void>({ schema, storage })
		}

		// Try to load from R2 (legacy storage, only happens once per room)
		if (this.roomId) {
			const r2Object = await this.env.TLDRAW_BUCKET.get(`rooms/${this.roomId}`)
			if (r2Object) {
				const snapshot = (await r2Object.json()) as RoomSnapshot
				const storage = new SQLiteSyncStorage<TLRecord>({ sql, snapshot })

				// Optionally delete the R2 object after successful migration
				// await this.env.TLDRAW_BUCKET.delete(`rooms/${this.roomId}`)

				return new TLSocketRoom<TLRecord, void>({ schema, storage })
			}
		}

		// No existing data - create fresh room
		const storage = new SQLiteSyncStorage<TLRecord>({ sql })
		return new TLSocketRoom<TLRecord, void>({ schema, storage })
	}
}
```

#### Step 3: Update your worker exports

Make sure both classes are exported from your worker entry point:

```tsx
export { TldrawDurableObject, TldrawDurableObjectSqlite } from './TldrawDurableObject'
```

The `loadRoom` function checks SQLite first (fast path for already-migrated rooms), falls back to R2 if SQLite is empty (one-time migration), and creates fresh storage for new rooms. You can optionally delete R2 data after migration to save storage costs.

Once all your rooms have been accessed at least once, the migration is complete. You can then remove the R2 fallback code and the stub `TldrawDurableObject` class.
